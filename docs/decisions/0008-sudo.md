# 0008 · Root access on the bastion

- **Status:** Accepted
- **Date:** 2026-10-01
- **Phase:** P0

## Context

`mgmt-01` is the administrative entry point of the lab, so a record of who ran what as root is part of its job. A root password was set during installation. In that case the Debian installer keeps the root account active and does not install `sudo` ([Debian installation guide](https://www.debian.org/releases/trixie/amd64/ch06s03.en.html)). Until now, administrative commands ran through `su -l -c`.

On 2026-10-01 the journal showed what `su` records: who became root, when, and failed attempts (`FAILED SU (to root) yamekuro on pts/0`), but never the command.

## Options considered

| Option | For | Against |
|---|---|---|
| **Install `sudo`, add `yamekuro` to the `sudo` group and keep the root password** | Every command is logged with the user who ran it; the root password stays as a way back at the console while `sudo` is new | One more setuid program; two secrets give root, and `su` still runs commands without recording them |
| Install `sudo` and lock the root password, as Debian does when none is set | A single secret, and every root command is logged | `su` stops working; a mistake in the `sudo` configuration leaves only rescue boot as a way back |
| Keep `su` | No change | Only who became root and when is recorded |

## Decision

- Install `sudo` and add `yamekuro` to the `sudo` group. Debian's default policy gives that group full `sudo` rights, with the user's own password.
- Keep the root password in KeePassXC for emergencies at the console. Use `sudo` for administration, and `su` only when `sudo` fails.
- Lock the root password in P1, once `sudo` has proven itself and the bastion's logs reach Wazuh.

Sources: [sudoers(5)](https://www.sudo.ws/docs/man/sudoers.man/), on logging successful and failed attempts to syslog by default; [Debian Security Tracker](https://security-tracker.debian.org/tracker/CVE-2025-32463), which lists trixie's `1.9.16p2-3+deb13u2` as fixed for CVE-2025-32463; and [Wazuh](https://wazuh.com/blog/detecting-common-linux-privilege-escalation-techniques-with-wazuh/), whose built-in rule 5402 fires on a successful `sudo`.

## Consequences

- Verified on 2026-10-01: the installed package is `sudo 1.9.16p2-3+deb13u2`. The journal records each command with user, terminal, directory, target user and command, for example `yamekuro : TTY=pts/0 ; PWD=/home/yamekuro ; USER=root ; COMMAND=/usr/bin/true`. Failed passwords are recorded with the command that was attempted (`2 incorrect password attempts`).
- `yamekuro` is not in the `adm` or `systemd-journal` group, so reading the system journal also needs `sudo`, and is itself logged.
- Commands run through `su` are still not recorded. That gap closes when the root password is locked in P1.
- To revert, remove `yamekuro` from the `sudo` group (`gpasswd -d yamekuro sudo`) and purge the package.
